# Rendering bridge

`DDIOSPainter` implements the `DDPainter` protocol generated by J2ObjC from
`com.dddumpling.game.Painter`. `DDPainter` is therefore the protocol name;
the native class has a distinct name to avoid an Objective-C symbol conflict.

The frame owner assigns its current `CGContextRef` to `painter.context`, then
calls the translated `DDRenderer` as it would on Android. The painter does not
retain the context: a UIKit drawing context is valid only for that draw pass.

## Coordinate and drawing contract

All primitive coordinates are UIKit screen coordinates (origin at the upper
left, y increasing down). ARGB Java `int` colours are unpacked into Core
Graphics red, green, blue, and alpha components. Closed shapes and contour
fills use the same winding behavior as `CanvasPainter`; `fillContours` uses
Core Graphics' even-odd fill rule so inner contours make transparent holes.

Strokes use round caps and joins. `arc` accepts screen-space degrees with zero
at the right edge and increasing clockwise, as Android `Canvas.drawArc` does.
The implementation builds each elliptical arc from cubic segments rather than
using Core Graphics' clockwise flag, whose apparent direction changes with a
UIKit-flipped context.

`save`, `restore`, `clipRect`, and `translate` directly map to their Core
Graphics state operations. A clip therefore remains active until its matching
`restore`, matching the Java painter contract.

## Text

The app bundles `Bungee-Regular.ttf` and registers it as `Bungee-Regular`.
Both Java text weights use Bungee because the typeface already provides its
heavy character. If the font cannot be registered, the painter uses the
medium or bold system face, matching the Android fallback policy.

Text is drawn through Core Text so the supplied y coordinate is an exact
baseline. Core Text's y-up glyph convention is flipped around that baseline
inside a saved graphics state; this keeps text upright in UIKit's y-down
context. Alignment is applied to the line's typographic advance: `-1` is
left, `0` is centered, and `1` is right.

## Reference-capture review

The debug renderer capture and Java reference harness both rendered fresh
640×1400 scenes with seed 42 after 30 updates at 1/60: title, play, stages 5,
10, 15, and 20, display case, Starpath, and Steamer. The paired contact sheet
is written to `ios/build/render-contact-sheet.png`; the numerical diagnostic
is `ios/build/render-comparison.txt`.

Visual review found the same scene composition, geometry, clipping, arc
direction, and boss/minigame placement in all nine pairs. The remaining
differences are expected: Core Graphics provides subpixel antialiasing and
native Bungee text, while `RasterPainter` uses a deliberately approximate
bitmap font. The diagnostic therefore is not a pixel baseline; it records the
known font and coverage differences for regression triage.

The title's deliberately oversized art can meet a safe-area edge because it
comes from the shared title renderer. It is present in the Java reference too,
so it is not an iOS clipping regression. No material painter discrepancy was
found or changed in this review.
